# FlexGuard / FlexBench：审核严格程度变化时还能判准吗

> ACL 2026 主会长文。定位：内容审核 benchmark 与模型方法，不是完整的 Agent 工具执行基准。

## 论文事实

§3 描述 FlexBench：4000个样本，2000个用户输入、2000个输入—回复对，覆盖7类核心风险。样本具有五档严重程度：BENIGN、LOW、MODERATE、HIGH、EXTREME，再映射成三种口径。

- strict：仅 BENIGN 判安全。
- moderate：BENIGN、LOW 判安全。
- loose：BENIGN、LOW、MODERATE 判安全。

这些是论文的实验定义，不是任何实际平台必须采纳的规则。

## 严重程度与处置决策为什么要分开

一个内容的风险程度可以相对稳定，但不同业务场景对风险的容忍度不同。把风险估计与部署阈值分开，才便于研究审核口径改变时的表现。

FlexGuard 输出连续风险分数，通过阈值作不同口径下的二分类。分数不是天然的违规概率；它要经过论文中的训练和校准。不要把“80分”自动解释为“80%概率违规”。

## 评测重点

分别报告输入审核和回复审核；分别报告三种口径；再比较平均与最差口径 F1。只汇报平均分可能掩盖某一口径下的显著退化。

论文表1区分 rubric thresholding 与 calibrated thresholding。公平比较要说明基线是否也允许验证集阈值调整，不能只给自己的模型最佳校准，而让基线固定默认阈值。

## 一个教学例子

虚构内容 X 被标为 LOW。严格模式下判违规，中等与宽松下判安全。系统如果始终输出同一标签，可能在一个口径得分很好，在另一个口径明显失误。此时问题不一定是内容理解能力，而是条件化决策没有随政策变化。

但是现实政策并不总是沿单轴变宽或变严。业务 A 允许某类内容、禁止另一类，业务 B 恰好相反，不能用一个全局阈值解决。需要结合 GMP 式细粒度规则理解。

## 用于审核 Agent 时，还缺哪些测试

- Agent 是否读到正确版本的政策？
- 口径切换后是否清理旧缓存或旧结论？
- 高分风险是否按正确流程升级人工？
- 文本、图片与上下文冲突时如何处理？
- 最终处置是否对应同一个内容对象？

因此 FlexBench 可以测试 Agent 的判定模块，但不能单独证明整个工作流可靠。

## 复现实验建议

固定验证集调阈值，再锁定测试集；按每类风险、每种口径、输入与回复分别看误杀和漏检。额外设一个不参与调参的时间外或业务外集合，检查阈值迁移。
