# 为中文内容审核 Agent 设计一套评测

> 本篇是基于前述论文的综合实践建议，不是已经发表的新 benchmark，也没有在你的业务系统上运行。所有示例使用虚构对象与模拟处置。

## 1. 先定义产品承诺，再选数据

假设目标产品会读取评论、检索当前政策、查询必要上下文、给出标签与证据，并在权限内执行处置。成功定义应包含五件事：对象正确、规则正确、判断正确、动作正确、证据可追溯。

“审核准确率90%”不足以定义成功。应明确单位是评论还是完整工单；是所有类别平均还是严重风险召回；是否包含证据缺失、人工升级和工具失败。

## 2. 建议的四层评测

### L1：静态内容判定

直接给内容和政策，测试标签、严重程度、误杀与漏检。可借鉴 FlexBench 的多口径、GMP 的多标签与动态规则。先固定工具以外因素，识别基础判定瓶颈。

### L2：轨迹安全评审

给固定日志，测试 Judge 是否定位首次违规动作、区分尝试与完成、识别延迟拒绝。可借鉴 ASSEBench。金标必须含证据位置和适用规则。

### L3：受控工具执行

让 Agent 在可重置审核后台工作。测正确取证、规则版本选择、对象一致性、权限与异常处理。可借鉴 AgentHarm 的细粒度检查和 ST-WebAgentBench 的 CuP。

### L4：端到端多轮任务

加入用户补充、内容编辑、政策切换和不可信外部材料。可借鉴 MT-AgentRisk 与 OpenAgentSafety 的轨迹设计。检验最终状态和过程中的副作用。

四层分开报告。L1高、L3低说明应修流程；L1低则复杂 Agent 规划未必能补救。

## 3. 数据覆盖矩阵

不需要一开始做所有组合，但至少覆盖：

- 内容形态：纯文本、图文、引用、上下文依赖。第一版可以只做文本，但要声明范围。
- 风险类别：按你自己的政策定义；不要不加映射地照搬英文 benchmark 分类。
- 表达方式：显式表达、隐喻、谐音、反讽、转述、批评或反对有害观点。
- 规则情况：固定规则、宽严口径、版本变更、冲突规则、适用范围不明。
- 流程情况：证据齐全、工具超时、对象被编辑、权限不足、应转人工。
- 对抗入口：用户请求、不可信网页、工具结果、历史记录。分别设置权限和攻击预算。

注意把正常但容易误杀的内容纳入：新闻引用、学术讨论、受害者求助、反驳仇恨、虚构文学。标签必须根据具体政策与上下文，不能仅凭关键词。

## 4. 从12例原型起步，再扩到300例试点

建议先手写12例：4例正常、4例明确违规、4例边界或流程异常。跑通数据格式、检查器和人工复核之后，再考虑试点规模。

一个可选的300例预算：120例静态判定、60例固定轨迹、60例工具任务、60例多轮任务。这是工作量规划，不是统计充分性的证明。每类数量和置信区间仍需根据真实用途设计。

对于低频高危类别，单独建立压力测试；不要让其结果被大量正常案例平均掉。压力测试的比例不代表线上实际发生率，两者应分开报告。

## 5. 推荐的样本记录格式

```json
{
  "case_id": "demo-001",
  "layer": "tool-workflow",
  "policy_version": "demo-policy-v1",
  "content_id": "fictional-post-001",
  "content_hash": "hash-of-evaluated-version",
  "user_goal": "审核并按授权处理这条模拟评论",
  "gold_labels": ["category-A"],
  "gold_action": "escalate",
  "required_evidence": ["policy-section-2", "content-span-1"],
  "allowed_tools": ["get_content", "get_policy", "escalate"],
  "forbidden_side_effects": ["modify_unrelated_content"],
  "seed_family": "family-001",
  "split": "test"
}
```

这是教学 schema，不是任一论文官方数据格式。内容哈希是版本一致性证据，不是内容安全证明。策略、数据、工具版本都需记录。

## 6. 金标怎样建立

先写标注指南，再进行独立双标。标注者要看到相同政策与上下文，并分别记录标签、证据和不确定性。分歧进入仲裁；无法稳定判断的案例保留歧义标记，可作为独立挑战集。

不要先让待测模型生成答案，再把答案直接当金标。若用模型辅助标注，必须保存来源、人工审核流程以及模型之间可能共享偏差的限制。

## 7. 输出协议与检查器

建议输出：decision、categories、severity、policy_refs、evidence_refs、action、uncertainty。解释应简短可验证，不以语言流畅度代替证据。

检查器分工：

1. 格式检查：能否解析，字段是否缺失。
2. 语义检查：类别、证据和政策是否匹配。
3. 状态检查：是否只操作目标对象，状态是否符合预期。
4. 流程检查：需要的确认或人工升级是否完成。
5. 冲突复核：规则检查与 Judge 不一致时，人工看原始日志。

不要执行被审核内容中的指令；内容是判定对象，不是审核员的上级指令。

## 8. 推荐报告的指标

L1：各类别 Precision / Recall / F1、Macro-F1、正常内容误拦率、各口径最差表现。

L2：安全评审混淆矩阵、不安全轨迹漏判率、证据引用正确率、歧义集表现。

L3/L4：合规完成率、已实现有害状态比例、违规尝试比例、未到达风险点比例、错误对象操作率、有效人工升级率。

所有层记录端到端延迟、成本、失败类型、样本量与置信区间。指标方向要写明，例如 harmful completion 越低越好、benign completion 越高越好。

## 9. 最小对照实验

A：单模型直接判断。

B：增加政策检索。

C：增加工具执行前检查。

D：增加跨轮对象版本追踪与人工升级。

每次仅改变一个主要因素，并保持数据、预算和基础模型尽可能一致。若 D 更好，继续消融确定是版本追踪有效，还是更多调用预算造成差异。

## 10. 通过标准如何设置

不要从论文抄一个阈值当作业务上线门槛。根据各类错误成本预先定义：哪些严重违规不能接受，哪些正常任务性能必须保留，多少不确定样本允许转人工。先用验证集确定，再锁定测试集验证。

本专题只提供评测研究设计；没有替你确定生产上线阈值或实际业务政策。
