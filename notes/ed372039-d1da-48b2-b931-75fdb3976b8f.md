# 如何从读论文走到可复现的实验

## 1. 不建议一次部署十个 benchmark

先明确研究对象。若做内容审核 Agent，先用固定内容和政策评估判定层，再加工具。若做通用 Agent 的内容安全，先跑轻量合成工具基准，再进入网页环境。复杂环境会引入导航、登录和部署失败，容易掩盖真正的安全问题。

本专题没有安装或运行论文代码。以下是复现准备流程，运行前需按官方仓库当前版本核对依赖和命令。

## 2. 推荐的渐进顺序

### 第一步：人工复算10条

从合法可获取的数据中选择少量样本，手动读策略、轨迹和标签。能解释每条为什么 safe / unsafe，以及判定发生在哪里。如果无法手工理解，不要立即批量跑模型。

### 第二步：校验评测器

给评测器喂明确通过、明确失败、空输出、格式错误、尝试失败、延迟拒绝等案例。确认它不把超时默认当安全，也不把只说“已完成”当作真实完成。

### 第三步：冻结数据与协议

记录论文版本、代码 commit、数据 hash、模型版本、提示词、工具 schema、最大步数、温度、随机种子、超时重试和价格日期。API模型可能变化，应保存调用时间及可用版本标识。

### 第四步：小规模 smoke run

先运行少量任务，检查环境是否可重置、工具是否真的隔离、日志是否完整、评分是否可重复。基础设施错误单独统计，不静默删样本。

### 第五步：锁定后正式运行

调参只用训练 / 验证集；测试集只做最终评估。以原始任务家族划分，避免同一模板的改写穿透划分。所有失败和重试保留，不只挑成功轨迹。

## 3. 建议的实验目录

```text
experiment/
  protocol/      # 威胁模型、指标定义、预算
  versions/      # 代码、数据、模型、政策版本
  cases/         # 测试用例与划分
  trajectories/  # 原始交互日志
  states/        # 环境前后状态与关键证据
  judgments/     # 规则检查、Judge、人工仲裁
  reports/       # 汇总结果与误差分析
```

这是建议结构，不是任何仓库的安装说明。不要把真实用户敏感数据或访问密钥混入共享实验日志。

## 4. 每篇论文用同一组问题阅读

1. 被测对象到底是什么：执行 Agent、审核模块、Judge 还是规则生成器？
2. 主要用户是恶意还是善意？第三方能控制什么？
3. 样本单位是什么？多少原始任务，多少改写？
4. 工具是真实执行、固定模拟，还是 LLM 模拟？
5. 评测看最终文本、轨迹还是环境状态？
6. “失败”怎样计入？ASR 的分母是什么？
7. 是否有良性对照与过度拒绝分析？
8. Judge 是否有人工校验？
9. 数据是否重叠、受污染或进入经验库？
10. 哪些结论能迁移到你的业务，哪些不能？

## 5. 五种经常出现的虚假进步

**全部拒绝。** 有害完成率下降，但正常任务也无法做。解决：同时看良性能力与误拒。

**工具坏了。** 导航失败让危险行为没有发生。解决：报告到达风险点比例和基础设施失败。

**Judge 更宽松。** 系统没改善，评分器变了。解决：锁定评审协议，并用人工金标复核。

**测试泄漏。** 安全经验、提示词或调参见过测试任务。解决：按任务家族隔离，保存数据来源。

**只报平均。** 高频容易类别改善，关键长尾退化。解决：逐类、最差组和严重风险单独报告。

## 6. 一个误差分析记录模板

```text
case_id:
expected_policy:
actual_policy:
expected_decision:
actual_decision:
first_wrong_step:
observed_state_change:
root_cause_candidate:
judge_rule_disagreement:
proposed_fix:
regression_cases:
```

root_cause_candidate 应写“待验证原因”。例如怀疑模型忽略规则，就做保持其他条件不变的对照，不能只凭一条解释认定因果。
